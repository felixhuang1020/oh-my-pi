0示例代码与一句话结论

先把被测对象完整摊开，再谈机制。

# packages/ai/examples/example1.py  —— 全文 23 行
import asyncio

from pi_ai import create_models, SimpleStreamOptions
from pi_ai.providers.all import all_providers
from pi_ai.types import Context, UserMessage


async def main():
    models = create_models()                       # ① 建注册表
    for provider in all_providers():            # ② 造 9 个 provider
        models.set_provider(provider)              # ③ 注册

    model = models.get_model("deepseek", "deepseek-flash")   # ④ 查模型
    message = await models.complete_simple(       # ⑤ 发请求
        model,
        Context(messages=[UserMessage(content="hello", timestamp=0)]),
        SimpleStreamOptions(api_key="sk-120a2914135c4db7a4b3708a177a8cbb"),
    )
    print(message.content[0].text)          # ⑥ 取回文本
一句话结论：这段代码是「注册表模式 + 惰性代理 + 推送式事件流」的组合。它把「建 provider 表 → 查模型 → 发请求」三段职责分别交给 ModelsImpl（注册表 / 认证 / 分发）、ProviderImpl（按 model.api 选实现）、LazyApi（按需 import 适配器）三层。 真正发 HTTP 的是 pi_ai/api/openai_responses.py，所有「同步返回 stream、初始化在后台跑」的语义由 lazy_stream + AssistantMessageEventStream 提供。
注意两处与「直觉」不同的设计：
  • deepseek 走的是 openai-responses 适配器（不是专用适配器）——见 providers/deepseek.py 的 lazy_load("pi_ai.api.openai_responses")。
  • complete_simple() 内部调用的是同步方法 stream_simple() 再 .result() ——「同步返回 + 异步结算」，而不是一个直接的 async 请求函数。

3三阶段执行逻辑详解

把上面 24 步归并成三个语义阶段：构建注册表 → 解析模型 → 请求与结算。

阶段 A · 构建注册表（create_models + all_providers + set_provider）

create_models() 是 ModelsImpl.__init__ 的薄封装，它把四个可替换的协作者一次性装配好并全部留出「注入点」（CreateModelsOptions）：

字段默认实现职责
_providers{}（dict）provider id → ProviderImpl 的注册表
_credentialsInMemoryCredentialStore已存储凭据的读写（登录 / 登出也走它）
_models_storeInMemoryModelsStore动态模型目录的持久化快照
_auth_contextdefault_provider_auth_context()环境变量 / 环境文件的读取入口
_refresh_generations / _refresh_controllers / _publication_chains：三个 per-provider 的 dict，实现「代次校验取消 + 发布串行化」

all_providers() 等价于 TS 版 builtinProviders()：按 types.KNOWN_PROVIDERS 的顺序，从 _PROVIDER_FACTORIES 逐家调用工厂，共 9 家 —— anthropic / google / openai / deepseek / minimax / minimax-cn / moonshotai / moonshotai-cn / xiaomi。其中与本次示例相关的是：

# providers/deepseek.py（全文 28 行）
def deepseek_provider() -> ProviderImpl:
    return create_provider(
        CreateProviderOptions(
            id="deepseek",
            name="DeepSeek",
            base_url="https://api.deepseek.com",                  # ← 备用 base_url
            auth=ProviderAuth(api_key=env_api_key_auth("DeepSeek API key", ["DEEPSEEK_API_KEY"])),
            models=list(chat_model_catalog("deepseek").values()),      # ← 静态基线模型
            api=lazy_api(lazy_load("pi_ai.api.openai_responses")),      # ← 关键：不 import
        )
    )

create_provider() 直接返回 ProviderImpl(options)。构造函数里有三个值得记住的判断：

  • single = options.api if hasattr(options.api, "stream") else None —— 因为 LazyApi 实现了 stream，所以它被认定为「一个实现服务所有模型」的单一实现；否则按 model.api 建映射。
  • 基线模型 _baseline_models = list(options.models)，动态覆盖层 _dynamic_models = [] —— 二者是两层，不是一层。
  • 只有当某个实现声明了 fetch_deferred / cancel_deferred 时，才把对应方法挂到实例上，否则属性根本不存在（配合 getattr(..., None) 探测）。

chat_model_catalog("deepseek") 带 @lru_cache，链路是 load_provider_data("deepseek")（读 providers/data/deepseek.json）→ flatten_chat_model_catalog → from_json(Model, ...)。该 JSON 的实际内容如下（已核实）：

deepseek-v4-pro（同一 JSON 分组内的另一条 chat 模型）

set_provider() 只有两行，但第一行是整套并发安全设计的关键：

  • _supersede_provider_refresh(provider.id) —— 把该 provider 的刷新代次 +1，并 abort() 掉上一轮仍在跑的刷新控制器。这就让任何「旧代次的发布」在 _publish_provider_models 里被代次校验直接丢弃。
  • self._providers[provider.id] = provider —— 按 id 做 upsert，因此重复调用 set_provider 是幂等替换。

阶段 B · 解析模型（get_model）

同步方法，三次跳转：get_model("deepseek","deepseek-flash") → get_models("deepseek") → ProviderImpl.get_models() → _current_models()。合并规则是「类型与 id 都相同则原地替换基线条目，否则追加」：

def _current_models(self) -> list[AnyModel]:
    merged = list(self._baseline_models)              # ① JSON 目录里的静态模型
    for model in self._dynamic_models:            # ② refresh_models 拉到的动态覆盖
        index = next((p for p, e in enumerate(merged)
                      if get_model_type(e) == get_model_type(model) and e.id == model.id), -1)
        if index >= 0: merged[index] = model        # 覆盖
        else:         merged.append(model)         # 新增
    return merged

本示例未调用 models.refresh()，所以 _dynamic_models 为空，命中项直接来自 JSON 基线。

阶段 C · 请求与结算（complete_simple）

C1
transcript = normalize_context(context)
Context 的 system_prompt/tools 被折叠成一条前导 SystemMessage；本示例两者皆空，故 TranscriptContext.messages == [UserMessage("hello")]。该函数是生成 TranscriptContext 的唯一入口，且对已规范化的输入幂等。
C2
lazy_stream(model, setup) —— 第一层惰性
立即构造 AssistantMessageEventStream 并 ensure_future(run())，然后同步返回。调用方拿到的不是数据，而是一个「稍后会被填满的流」。
C3
setup(): _require_chat_provider + _apply_auth
_require_chat_provider 先 assert_chat_model 再用 model.provider 取 provider。_apply_auth 是认证注入的唯一收口：解析认证 → 合并 api_key / headers / env → 若解析结果带 base_url 则 replace(model, base_url=...)，最后 replace(options, ...) 产出 request_options。
C4
provider.stream_simple → _dispatch → _api_for(model)
_api_for 返回 _single（即 LazyApi）；若为 None 则返回一个「首次消费即抛错」的惰性流，把配置错误也统一编码进事件流而不是抛异常。
C5
LazyApi.stream_simple —— 第二层惰性
又套一层 lazy_stream；setup 里才 importlib.import_module("pi_ai.api.openai_responses")。这就是「import 几千行 adapter」的代价被推迟到首次请求的原因。
C6
openai_responses.stream_simple → stream() —— 第三层惰性
stream_simple 先用 build_base_options 把 provider 无关选项投影为 OpenAIResponsesOptions，随后 stream() 再建一个 AssistantMessageEventStream 并 ensure_future(run())。
C7
run(): HTTP + SSE 折叠
_create_client 造 httpx.AsyncClient（含 Authorization: Bearer …、User-Agent、会话粘性头）→ _build_params 造请求体 → retry_provider_request(send_streaming_request) 发 POST → push(start_event) → process_responses_stream(iter_stream_payloads(response)) 逐条折叠 → push(done_event) + end()。
C8
await ….result() 取回结果
done_event 被 push 时，_is_terminal_event 判定其为终止事件 → _settle(_extract_final_message(event)) → 取出 event.message，唤醒所有 result future。于是 complete_simple 的 await 得到完整的 AssistantMessage。
为什么用 simple 而不是普通 stream？ SimpleStreamOptions 是 StreamOptions 的超集，多出 tool_choice / reasoning / deferred / thinking_budgets 四个 provider 无关字段。_apply_auth 的注释明确指出：chat 路径刻意用 SimpleStreamOptions 作为兜底对象，因为 adapter 可能读取只存在于 simple 类型的字段——Python 下若不提供会抛 AttributeError 而非像 TS 那样得到 undefined。

4三层 lazy_stream 嵌套机制

这是本示例最容易被忽略、也最关键的结构：三次「同步返回 + 后台填充」的叠加。

唯一真正的「同步阻塞点」是最后的 await ….result()。此前所有操作——包括 create_models、all_providers、get_model、normalize_context、以及三层流的构造——都在当前 tick 内完成，一个字节的网络数据都还没发出去。

易踩的五个坑

  • 别以为 complete_simple 是 async 网络调用——它内部是「同步取流 + await 结果」。异常因此优先表现为 AssistantMessage.stop_reason == "error"，而不是 raise。要判断失败必须检查 stop_reason / error_message。
  • api_key 只走 SimpleStreamOptions，不写进环境变量时也能生效，因为 resolve_provider_auth 的第 1 优先级就是 overrides。反过来，一旦传了 key，provider 自带的 DEEPSEEK_API_KEY 就被完全绕过。
  • base_url 有两处来源：provider 的 CreateProviderOptions.base_url（本例 https://api.deepseek.com）与模型目录里的 baseUrl。运行时实际用的是 model.base_url（join_url 的入参），除非认证解析显式返回了 auth.base_url。
  • 三层 event stream 会让调用栈变深。排错时不要只看 openai_responses，要顺着 push → forward_stream → _settle → result 检查事件是否真的上浮到了最外层。
  • 只有 chat 类型模型会被 get_model 找到；get_models_of_type / get_all_models 才是全类型入口。本项目已裁掉 image / classifier 目录。
一句话复述整体机制：create_models() 装好一个空注册表 → all_providers() 造 9 个「只带惰性代理」的 ProviderImpl → set_provider() 把它们放进按 id 索引的字典 → get_model() 从静态 JSON 目录里取出 deepseek-flash → complete_simple() 用 normalize_context 规范化上下文、用 _apply_auth 注入认证、经三层 lazy_stream 把请求一路惰性下传到 openai_responses、 由 send_streaming_request 发出 POST、由 process_responses_stream 把 SSE 折叠成 AssistantMessage、最后由 done_event 触发 _settle 结算 .result()， 把 content[0].text 交回给 print。
